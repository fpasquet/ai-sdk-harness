# ai-sdk-harness

## Project overview

Open-source monorepo of community packages for the Vercel AI SDK harnesses (`@ai-sdk/harness`): publishable packages under `packages/*`, a Next.js example app, shared `@repo/*` workspace presets, an English-only Fumadocs site, and the CI and release automation that publishes to npm.

| Package                       | Path                            | What it is                                                                                               |
| ----------------------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `ai-sdk-sandbox-sbx`          | `packages/sandbox-sbx`          | A Docker Sandboxes (`sbx`) sandbox session for `HarnessAgent`, local or in the cloud                     |
| `ai-sdk-sandbox-microsandbox` | `packages/sandbox-microsandbox` | A microsandbox sandbox session for `HarnessAgent`: a local microVM booted from any OCI image             |
| `ai-sdk-sandbox-cloud-run`    | `packages/sandbox-cloud-run`    | A Cloud Run sandbox session for `HarnessAgent`, and the sandbox service that runs the sandboxes          |
| `ai-sdk-sandbox-gce`          | `packages/sandbox-gce`          | A Compute Engine sandbox session for `HarnessAgent`: the service, egress proxy and in-VM agent behind it |
| `ai-sdk-sandbox-runtime`      | `packages/sandbox-runtime`      | An Anthropic Sandbox Runtime (srt) sandbox session for `HarnessAgent`, on this host                      |
| `ai-sdk-harness-plugins`      | `packages/harness-plugins`      | Plugins for `HarnessAgent`: tools, skills, commands, hooks, subagents, MCP servers                       |
| `ai-sdk-harness-sessions`     | `packages/harness-sessions`     | The lifecycle of `HarnessAgent` sessions: suspended when idle, resumed, several in one sandbox           |
| `ai-sdk-harness-workspace`    | `packages/harness-workspace`    | A Git checkout for each `HarnessAgent` session, a worktree in its sandbox, its changes a patch           |
| `ai-sdk-harness-approval`     | `packages/harness-approval`     | An approval policy for `HarnessAgent` tool calls, grants for a session, the agent's questions            |
| `ai-sdk-harness-network`      | `packages/harness-network`      | The hosts a `HarnessAgent`'s sandbox may reach, and the closed network policy built from them            |

Constraints:

- Open source, MIT licensed.
- Packages are published unscoped, named `ai-sdk-<kind>-<provider>` (`ai-sdk-harness-<feature>` for what extends the agent rather than giving it a sandbox), by the release workflow through npm trusted publishing (OIDC). Only the first version of a new package is published by hand, from the `fpasquet` npm account, as `MAINTAINERS.md` describes. Check that a name is free on npm (`npm view <name>` answers E404) before creating a package.
- The packages are in their **0.x** series: they are released to be tried, and their API settles with that feedback before a 1.0.0. See [Versioning](#versioning).
- Only Node `>=24.0.0` is supported. CI tests Node 24 and 26.
- Packages are ESM-only, like the AI SDK they plug into. Public APIs are importable from the package root only.
- The documentation site targets package consumers, never maintainers of the monorepo itself: maintainers read `CONTRIBUTING.md` and `MAINTAINERS.md`.

---

## Technical stack

pnpm workspaces, TypeScript (strict, `nodenext`), Vitest for tests, ESLint + Prettier, Turborepo for task orchestration, Changesets for versioning and publishing, Next.js for the example and Fumadocs (Next.js + MDX) for the documentation site. Exact versions live in the respective `package.json` files, pnpm's in the root `packageManager`.

Shared ESLint / Prettier / TypeScript / Vitest rules live in `packages/configs/*` and are consumed as `@repo/*` packages with `workspace:*`. Never duplicate compiler, lint, or test options downstream: extend the preset.

pnpm only runs the install scripts of the dependencies listed in `pnpm-workspace.yaml#allowBuilds`, and fails the install on any other: a new dependency that needs one goes there.

## Architecture

The agent should introspect the workspace before editing; only the non-obvious rules are listed here.

- `packages/<name>` is the only path for publishable packages. New packages mirror the shape of `packages/sandbox-sbx`.
- The client code of a sandbox package (`src/` of `ai-sdk-sandbox-sbx` and `ai-sdk-sandbox-microsandbox`, `src/client/` of `ai-sdk-sandbox-cloud-run`, `ai-sdk-sandbox-gce` and `ai-sdk-sandbox-runtime`) is split into the same folders, so the packages read alike: `errors/` (public errors), `utils/`, `transport/` (the only way to reach a sandbox), `network/` (what crosses the sandbox's boundary: credentials and ports; `ai-sdk-sandbox-sbx` only, the Cloud Run service handles it on its side), `session/` (the `SandboxSession` implementations) and `lifecycle/` (create, resume, templates). Its root keeps the settings types and `provider-id.ts`. No barrel files: `src/index.ts` is the only one.
- Each layer of a client only imports the ones below it: `errors/` and `utils/` import nothing of the package, then `transport/` ← `network/` ← `session/` ← `lifecycle/`. `sandboxClientLayers()` of `@repo/eslint-config/boundaries` enforces it with `no-restricted-imports`, and each package's `eslint.config.mjs` declares its other boundaries the same way. A new boundary goes there, not in a review comment.
- `packages/configs/*` are private `@repo/*` presets, never published.
- `examples/*` are consumer-side demonstrations. They are in `.changeset/config.json#ignore` and never enter the release flow. `examples/next-chat` runs on any of the sandbox packages: `EXAMPLE_SANDBOX` (`sbx` by default, `microsandbox`, `cloud-run` or `srt`) picks the sandbox, see its `.env.example`. Its conversations are sessions of `ai-sdk-harness-sessions`, kept in `.data/sessions` (ignored by Git: it holds resume states). It runs every official `@ai-sdk/harness-*` adapter (`lib/harness-adapters.ts`), its credentials read from the environment only: subscriptions for Claude Code, Codex and fx, `OPENROUTER_API_KEY` for OpenCode, Pi, Cline, Deep Agents and Grok Build, never AI Gateway. Its adapters are pinned to the release wave of the workspace's `@ai-sdk/harness`: from `@ai-sdk/harness-claude-code` 1.0.163 on, the bridge-backed adapters ship without `dist/bridge/pnpm-lock.yaml` and fail their bootstrap, so check a newer wave has it back before bumping them.
- `docs/` is a Fumadocs site, built as a static export and deployed to Cloudflare Pages on pushes to `main`, independently of package releases. Static export means no server at runtime: every route is prerendered and images are served unoptimized. Package pages (`content/docs/packages/*.mdx`) `<include>` the package README: the README is the single source of a package's documentation. API reference pages (`content/docs/api-reference/*.mdx`) render the settings types with `<AutoTypeTable>`. `docs/AGENTS.md` holds the Next.js rules of the site.
- `scripts/` holds repository tooling (`generate-screenshots.ts`), not runtime code.

### `ai-sdk-sandbox-sbx`

- Mirrors the API shape of `@ai-sdk/sandbox-vercel`: `createSbxNetworkSandboxSession()` / `resumeSbxNetworkSandboxSession()` returning a `HarnessV1NetworkSandboxSession`, `restricted()` returning an `Experimental_SandboxSession`.
- The `sbx` CLI is the only way the package reaches a sandbox (`src/transport/sbx-cli.ts`). Arguments go to `spawn` as-is, never through a host shell; in-sandbox scripts (`src/transport/sandbox-scripts.ts`) take their inputs as positional arguments.
- `src/network/` holds what crosses the sandbox's boundary: credential brokering through the Docker Sandboxes proxy and published ports.
- Behaviours of the `sbx` policy checked on the real CLI (v0.46): a rule scoped to a sandbox (`--sandbox`) goes with it; a deny wins over any allow, a narrower one included, so `deny **` cannot be combined with allows; a sandbox-scoped `allow **` lifts the proxy's fence around private networks and the metadata server, and an allowed name is not checked against CIDR rules; `policy rm` needs `--force` without a terminal. `src/network/network-policy.ts` builds on them. Checked on v0.48: `sbx policy log <name> --type network --json` prints `{ allowed, blocked }` for that exact name (a prefix matches nothing, an unknown name prints empty lists), one entry per host and port with `count`, `first_seen` and `last_seen`, kept once the sandbox is removed and inherited by a new one of the same name, and still listed as blocked once the host is allowed; `--limit` applies to each list; a name lookup the proxy's DNS refuses is logged without a port, beside the same name under the search domain `<sandbox>.docker.internal`, and reverse lookups (`in-addr.arpa`) are logged too. Only a host no rule allows gets a pending approval (`sbx policy approval ls`, a table with no JSON output), which goes with the sandbox and comes back on the next request once dismissed; a host a rule denies gets none. `sbx --cloud policy log` reads the account's log, not tried without a cloud subscription. `src/network/blocked-requests.ts` builds on them. Upstream issues: [docker/sbx-releases#706](https://github.com/docker/sbx-releases/issues/706) (secret value on the command line), [#707](https://github.com/docker/sbx-releases/issues/707) (secret restricted to a header).
- Unit tests run against `test/fake-sbx.mjs`, a stand-in `sbx` that runs `exec` on the host in a temporary directory. `test/*.e2e-spec.ts` run against the real `sbx` and are not part of CI (GitHub runners have no Docker Sandboxes).

### `ai-sdk-sandbox-microsandbox`

- Mirrors the API and the folders of `ai-sdk-sandbox-sbx`: `createMicrosandboxNetworkSandboxSession()` / `resumeMicrosandboxNetworkSandboxSession()`.
- The `microsandbox` SDK (a native addon that ships the `msb` runtime) is the only way the package reaches a sandbox, and only `src/transport/` imports it at runtime. Commands go to the in-VM agent as an argument array, their variables on the SDK's channel; in-sandbox scripts (`src/transport/sandbox-scripts.ts`) take their inputs as positional arguments. File operations are commands too, run as the sandbox's user, so the files the harness writes are that user's.
- Behaviours of microsandbox its docs leave out, checked on the real runtime: the SDK only launches a runtime of its own version, and one installed in `~/.microsandbox` wins over the bundled one; a secret with a new placeholder, and TLS interception, need a restart of the microVM (`modify({ policy: 'restart' })`, which kills the running commands), a new value for a known placeholder is live; HTTPS hosts only match a network policy, and secrets only reach HTTPS requests, with TLS interception on; ports and the network policy are fixed at creation; a disk snapshot keeps the disk alone, so a restore sets resources, user, ports and mounts again; a command ends when the client that started it disconnects; reading a directory through the SDK's `fs` hangs; a restored sandbox does not intercept TLS until it holds a secret, and `Sandbox.restore()` cannot turn it on (hence the `MICROSANDBOX_TLS_INTERCEPTION` sentinel); an allowed egress by default reaches the host's own services (`host.microsandbox.internal`); a deny-by-default policy resolves the names its domain rules list, but a `public` group rule needs DNS to the gateway (`host` group, port 53) allowed. `config()` reports `maxTcpConnections` as `network.maxConnections`; the `restricted` profile (the package's default) runs Claude Code fine, and a restore accepts it; `Sandbox.restore()` refuses an owned volume, but a disk snapshot carries the owned disks of its sandbox, a copy to each restored one; `/run` lives on the sandbox's disk, so pid files outlive a stop; a job (`execDetachedWith`) outlives the client, not a restart of the microVM; containers in the sandbox do not trust microsandbox's CA unless the bundle is mounted in them, and Docker Hub serves layers from both `production.cloudflare.docker.com` and `production.cloudfront.docker.com`. Keep them in mind before changing how the package drives the SDK.
- Upstream issues the package works around, linked from its README where it says so: [microsandbox#1835](https://github.com/superradcompany/microsandbox/issues/1835) (`modify()` cannot restrict a secret to its header), [#1836](https://github.com/superradcompany/microsandbox/issues/1836) (`restore()` cannot turn TLS interception on), [#1837](https://github.com/superradcompany/microsandbox/issues/1837) (no connection to a guest port without publishing it). Existing ones it documents: [#1538](https://github.com/superradcompany/microsandbox/issues/1538) (network policy of a running sandbox), [#1183](https://github.com/superradcompany/microsandbox/issues/1183) (secrets never stored), [#1780](https://github.com/superradcompany/microsandbox/issues/1780) (ports, not in the Node.js SDK yet). Removing a snapshot leaves the sandboxes restored from it running and starting. microsandbox refuses to remove the latest snapshot of a group, its head, while the group holds others, `force` or not: templates are saved in no group. Check them before working around the same limits again.
- The real value of a brokered credential is stored by microsandbox in its SQLite database on the host: the README says so, keep it said.
- Unit tests resolve `microsandbox` to `test/fake-microsandbox.ts` (a Vitest alias), a stand-in SDK that runs commands on the host in a temporary directory per sandbox, guest paths mapped into it. `test/*.e2e-spec.ts` run against the real runtime, are skipped without KVM or Apple Silicon, and are not part of CI.

### `ai-sdk-sandbox-cloud-run`

- One folder per runtime under `src/`. The client (`src/client/`, exported from `src/index.ts`) mirrors the API and the folders of `ai-sdk-sandbox-sbx`: `createCloudRunNetworkSandboxSession()` / `resumeCloudRunNetworkSandboxSession()`. The sandbox service (`src/server/`) is the package's `bin` (`ai-sdk-sandbox-cloud-run serve`, `src/server/cli.ts`), deployed in a Cloud Run service with `--sandbox-launcher`; it is not exported. They speak the HTTP API of `src/server/http/routes.ts`, whose bodies are typed once in `src/protocol/api.ts`, and the frames of `src/protocol/frames.ts`. The server never imports the client, nor the client the server: what they share lives in `src/protocol/`.
- The service is split by concern: `http/` (server, routes, streams, tunnels), `sandboxes/` (the sandboxes it manages), `runtime/` (the `sandbox` CLI of Cloud Run), `egress/` (proxy, policy, network guard) and `snapshots/` (snapshot stores). `cli.ts`, `config.ts`, `logger.ts` and `package-version.ts` stay at its root: `config.ts` and `package-version.ts` locate `in-sandbox/` and `package.json` relative to themselves.
- The service has no runtime dependency: plain `node:http`, and only type imports from `@ai-sdk/harness`. `src/in-sandbox/*` run inside the sandboxes with the image's Node.js and import nothing but `src/protocol/`.
- The `sandbox` CLI of Cloud Run is the only way the service reaches a sandbox (`src/server/runtime/sandbox-cli.ts`). It loses exit codes: every command runs under `ExitCodeCarrier`. Behaviours of the CLI that Google does not document were checked on the real Cloud Run; keep them in mind before changing how the service drives it.
- Security rules of the service, each with its tests in `src/security.spec.ts`: Cloud Run logs every command line it runs in a sandbox, so nothing but `node …/launch.js` may ever be on one (commands, variables and directories go on the launcher's stdin); a credential the service holds never enters a sandbox (`Sandbox.assertNoSecret`); the egress proxy never connects to a private address (`src/server/egress/network-guard.ts`), checked after DNS resolution, an IPv6 address carrying a private IPv4 one (NAT64, 6to4) included; the proxy takes the credentials it injected out of the response headers. `SANDBOX_ALLOW_EGRESS` opens a network beside the proxy, which Google does not document: never turn it on by default. Credential brokering is not optional.
- Unit tests start the real service in-process over `test/fake-sandbox.mjs`, which isolates nothing, and drive it with the real client. The suite builds the package first, into `node_modules/.cache/test-build` and never into `dist`, which an app running meanwhile imports (`test/build-helpers.ts`): the service runs the built `in-sandbox/*`. `test/*.e2e-spec.ts` run against a service deployed on Cloud Run (`CLOUD_RUN_SANDBOX_URL`) and are skipped without it.

### `ai-sdk-sandbox-gce`

- One folder per runtime under `src/`, each loaded alone by `src/cli.ts` (`ai-sdk-sandbox-gce serve|proxy|agent`): the client (`src/client/`, exported from `src/index.ts`), the sandbox service (`src/server/`, on Cloud Run), the egress proxy (`src/proxy/`, on a machine of its own) and the agent of each sandbox machine (`src/in-vm/`, run by systemd from the sandbox image). They share `src/protocol/` (the HTTP APIs: the service's, the same as `ai-sdk-sandbox-cloud-run`'s, the agent's and the proxy's administration API) and, on the servers' side, `src/common/` (HTTP helpers, logger, version); none imports another (`eslint.config.mjs`). The client is `ai-sdk-sandbox-cloud-run`'s, under other names: keep them in step.
- The service keeps nothing: Compute Engine says what a machine is (labelled `ai-sdk-sandbox=sandbox`, named `<prefix><sandbox>`, or, taken from the warm pool, named `<prefix>pool-<hex>` and labelled `ai-sdk-sandbox-name=<sandbox>`: Compute Engine cannot rename a machine), the proxy holds the allowed hosts and credentials, the agent runs the processes. Any Cloud Run instance serves any sandbox. A stop is a Compute Engine stop, the disk kept; a template is an image of a stopped builder's disk, named after the template id and a digest of the package version and the base image (a family resolved). The warm pool (`SANDBOX_WARM_POOL`, `SANDBOX_PROFILE=fast`) keeps machines booted from each template in use (`ai-sdk-sandbox=pool`), never one an agent ran in, and deletes one that waited 24 h; a creation takes one by changing its labels with their fingerprint, so that of two creations one wins, and makes the next one in the same request, without waiting for it: Cloud Run throttles the CPU once a request is answered. `POST /v1/prepare` with a template boots one machine of it into the pool (`ai-sdk-sandbox-prepared=true`) when its pool holds none, whatever the profile, deleted unused after 15 minutes as a call meets it; its agent powers it off itself 16 minutes after boot unless configured (metadata `ai-sdk-sandbox-idle-poweroff-minutes`, as root only, a marker in `/run` keeping a restarted agent from it).
- The service reaches Compute Engine over its REST API with `fetch` (`src/server/compute/`), never a client library: the servers have no runtime dependency, type imports of `@ai-sdk/harness` aside.
- Security rules, each with its tests in `src/security.spec.ts`: the machines get no external address, no service account and no credential of the service; an agent only answers the token the service derives for its machine and its run (`agentToken`, HMAC of `SANDBOX_AGENT_SECRET`), carried in `x-ai-sdk-sandbox-agent-token`, the run drawn anew at each stop; the proxy knows a sandbox by its machine's internal address alone and refuses any other, never connects to a private address after DNS resolution, only lets through a tunnel the TLS that names its host (SNI), keeps credentials in memory only and takes them out of response headers; a command carrying a credential the proxy holds is refused (`POST …/screen`).
- The service's image is the package's `Dockerfile`, published to Docker Hub by `images.yml` for each release, from the version on npm; the CI builds it from the packed package. `ai-sdk-sandbox-cloud-run` ships one the same way, which is also what its sandboxes see. The READMEs deploy them with `--image`.
- Unit tests run the real service and the real proxy in-process over `test/fake-compute.ts`, a fake Compute Engine API whose machines are agent processes of this host, built into `node_modules/.cache/test-build/dist` (`test/build-helpers.ts`), isolating nothing. Every machine is on 127.0.0.1: a test of the network uses one sandbox. `test/*.e2e-spec.ts` run against a service deployed on Google Cloud (`GCE_SANDBOX_URL`) and are skipped without it.

### `ai-sdk-sandbox-runtime`

- A sandbox is one process srt wraps, the supervisor (`src/in-sandbox/supervisor.ts`), that runs every command, file operation and port connection of the sandbox, so they share its filesystem view and, on Linux, its network namespace. The client (`src/client/`) drives it over its stdin and stdout with the frames of `src/protocol/frames.ts`; neither side imports the other, and the supervisor imports nothing but `protocol/` and Node.js built-ins: it is copied into the sandbox's directory at each start and runs with the host's Node.js.
- srt's `SandboxManager` is one per process: `src/client/transport/srt-runtime.ts` is the only code that touches it (through the `SrtManager` interface, which the tests fake), initializes it once and refuses other runtime settings afterwards. Per-sandbox network allow lists (`registerCommandNetworkLists`) are feature-detected: srt 0.0.79 lacks them and gets the union of every sandbox's list.
- Credentials go through srt's sentinel registry (`registerWithSentinel`): the harness's placeholder is the sentinel, swapped on egress past srt's TLS termination. srt cannot drop a sentinel: withdrawing one empties it and binds it to no host.
- What a sandbox may write is its `sandbox/` directory and its workspace; its `sandbox.json` and `.supervisor/` sit beside it, never writable, so nothing it does outlives its rules (`src/client/lifecycle/sandbox-directory.ts`, `filesystem-policy.ts`). The host user's home is hidden but for what the sandbox needs, srt's own package included (its `apply-seccomp` helper runs inside).
- `filesystemOf` always denies the sockets that drive the host (`hostControlPaths`: the session and system D-Bus, Docker, containerd, Podman), so `allowAllUnixSockets` cannot hand the agent the host's service managers or container engine. srt masks a file or a directory, not a socket, so a bare `.sock` is hidden by name only; keep high-value sockets in a `denyRead` directory. Where srt does not isolate networks (`isolatesNetworks` false, 0.0.79), `SrtRuntime.allow` refuses a second sandbox whose hosts differ instead of applying the union.
- Unit tests fake srt (`test/fake-srt.ts`: the command runs as it is) and run the real supervisor on the host, built into `node_modules/.cache/test-build` (`test/build-helpers.ts`). `test/*.e2e-spec.ts` run real sandboxes and a real Claude Code turn; not part of CI.

### `ai-sdk-harness-plugins`

- A plugin is plain data (`src/definitions/plugin.ts`). `withPlugins()` applies it to the settings of a `HarnessAgent`; it never wraps nor subclasses the agent.
- What depends on a runtime lives in `src/runtimes/`, one file per runtime, looked up by `harnessId` (`runtime-for.ts`): the features it takes, the native form of an MCP server, and what goes in a session's working directory. A runtime the package does not know takes tools, skills, commands and files only. Adding a runtime is a file there, and its rows in the tests.
- Everything written in the sandbox goes through `src/session/`: one `sh -c` script per step, whose inputs are positional arguments, never spliced into the script; a manifest (`.ai-sdk-harness/manifest.json`) records what was written so that a resume takes back what is no longer wanted.
- `describePlugin()` is what leaves the server: it must never carry a tool's code, a hook's command, a command's prompt, a subagent's instructions, a skill's content, nor an MCP server's URL, headers or environment. `src/catalog/plugin-catalog.spec.ts` checks it.
- A plugin, or an item on its own (one tool, skill, rule, command, hook, subagent or MCP server), is configuration: written in code or as JSON, checked alike by `definePlugin` / `defineItem` (`src/config/`). A tool is an AI SDK tool or a `ToolDefinition` (`http`, `sandbox-command`, or `registered`, the reference to a tool of the application), whose `inputSchema` is a JSON Schema or, in code, a zod or Standard Schema (`src/config/input-schema.ts`), each `{key}` of an `http` URL a required property of it, each `INPUT_<KEY>` a `sandbox-command` reads one of its properties (`src/config/input-variables.ts`), and what is accepted but likely a mistake — a parameter nothing reads, arguments a command's hint does not announce — a warning of `lintPlugin` rather than an error (`src/config/lint-plugin.ts`); secrets are `{ "secret": "<name>" }` references. `resolvePlugins` builds the definitions, resolves the secrets (`resolveSecret`: configuration never holds a secret, only `{ "secret": "<name>" }`) and connects the MCP servers — on the host by default, with `@ai-sdk/mcp`, an optional peer dependency imported on demand out of webpack's and Turbopack's sight (`webpackIgnore`, `turbopackIgnore`: an application without it still builds), its absence turned into an error that says to install it (`src/config/connect-mcp-server.ts`), or `connectMcpServer`; a `runIn: 'sandbox'` server may hold no secret. `withPlugins` builds on its own what needs none of that, and refuses the rest. The zod schemas of `src/config/plugin-schema.ts` and `item-schema.ts` are the one definition of the configuration, imported from `zod/v4` (a peer dependency): keep them in step with the types of `src/definitions/plugin.ts`.
- A marketplace is a catalog (`src/catalog/`) of plugins and items, each with an id (`plugin:<name>`, `<plugin>/<kind>:<name>`, `<kind>:<name>`). A selection is a list of ids, expanded with the items' `requires`, and a selected plugin's own `requires` (what it uses outside itself, delivered as the items they are); an item on its own resolves to a plugin of its own. What a selection comes to, what brings each id and what taking one out leaves are the catalog's (`src/catalog/selection.ts`): an application keeps a selection, never its own rules for it. `src/selection.ts`, published as `ai-sdk-harness-plugins/selection`, gives the same answers in a browser from `describe()`, through `entriesOfDescription()`: it may import nothing that runs on a server, and `src/selection.spec.ts` checks it answers as the catalog does.
- The folders are layered like the sandbox clients: `errors/` and `utils/` are leaves, then `definitions/` ← `commands/` ← `runtimes/` ← `session/` ← `mcp/` ← `config/`, and beside each other at the top `catalog/`, `loader/` and `agent/` (`eslint.config.mjs`).
- Unit tests run `onSession` against `test/host-sandbox.ts`, a stand-in sandbox on a temporary directory of the host, Git included; `test/fixtures/claude-plugin` is a Claude Code plugin with every part the loader reads, and `test/fixtures/mcp-server.mjs` an MCP server with no dependency, run on the host and in the sandboxes. `test/*.e2e-spec.ts` run real Claude Code and Codex turns in a Docker Sandbox and are not part of CI. The README shows the plugin and items of `examples/next-chat/marketplace/` beside their screenshots: `src/readme.spec.ts` keeps its JSON identical to theirs, so edit both together and retake the screenshots (`pnpm screenshots`) when a change shows.

### `ai-sdk-harness-sessions`

- A session manager (`createSessionManager()`, `src/manager/`) runs the sessions of any `HarnessAgent`: it never wraps nor subclasses the agent, and reads of it only `createSession`, `stream` and `continueStream` (`SessionAgent`, `src/definitions/agent.ts`), of a harness session only `stop`, `destroy` and `hasUnfinishedTurn`.
- Every change of status goes through one method, `transition()`, which writes the session to the `SessionStore` (queued per session by `SessionJournal`) and sends it to the subscribers. Starts run one at a time: the first one installs the harness in the sandbox. A resume keeps the store's record `suspended` until it is back, so a crash meanwhile leaves it resumable; a resume that fails stays `suspended` with its resume state.
- How a session gets a sandbox is a `SessionSandboxes` (`src/sandboxes/`): `sharedSandbox()` hands out views of one sandbox (`fork({ ports })` of `ai-sdk-sandbox-sbx` and `ai-sdk-sandbox-cloud-run`), one bridge port each; `sandboxPerSession()` a sandbox each.
- The manager reads a turn's UI message streams to their end (`src/turns/turn-stream.ts`) and passes their chunks on to the client, so the session is settled and written whether the client stays or not. A turn may run several streams: when it pauses on approvals the `approve` option answers, the next stream continues the same client message (`src/turns/approval-answers.ts`). What a paused turn waits for is read from its last message (`src/turns/pending-input.ts`).
- Several managers share a store through its ownership rows (`getOwnership`, `writeOwnership`, `renewOwnerships`, `releaseOwnership`), each one plain read or write that any ORM does: the claim logic is the manager's (`src/manager/session-leases.ts`), a compare-and-set on the row's `version`, and every session of a manager shares the expiry of its last renewal, so they expire together when it crashes. `createMemorySessionStore({ shared: true })` (`ai-sdk-harness-sessions/memory`, beside `./testing`) is the reference; `sessionStoreChecks()` (`ai-sdk-harness-sessions/testing`, no test runner imported) is the contract, run on the memory stores in `src/store/session-store-checks.spec.ts`. The README's Drizzle recipe was checked with it on PGlite.
- The folders are layered: `utils/` and `definitions/` (types and constants) are leaves, then `errors/` ← `store/`, `sandboxes/` and `turns/`, beside each other ← `manager/` (`eslint.config.mjs`).
- `src/tasks/` reads the task list the agent keeps (Claude Code's `TodoWrite`, `TaskCreate`, `TaskUpdate`) from a conversation, or call by call. It stands apart, a leaf importing nothing of the package, and is also published as `ai-sdk-harness-sessions/tasks` (`src/tasks.ts`), which runs in a browser: the registry's `agent-tasks` component imports it.
- Unit tests drive the manager with `test/fakes.ts`: an agent whose turns follow a script, built on `createUIMessageStream`, and sandboxes that record what they are asked. `test/*.e2e-spec.ts` run real Claude Code sessions in a Docker Sandbox and are not part of CI. The `examples/next-chat` screenshots `sessions`, `approval` and `resumed` show the package at work in its README.

### `ai-sdk-harness-workspace`

- A workspace (`createWorkspace()`, `src/workspace/`) ties a repository to the sessions of any `HarnessAgent` in two places, and never wraps the agent: `workspace.sandboxes()` wraps a `SessionSandboxes` of `ai-sdk-harness-sessions` (or `open()` a sandbox of yours) to know each session's sandbox, and `withWorkspace()` sets `sandboxConfig.onSession`, which checks the repository out in the `sessionWorkDir` the harness just made. The view of the sandbox a lease hands out is a `Proxy` of it whose `restricted()` views are recorded (`bySandbox`): that is how `onSession`, which only gets a restricted view, and a tool's `experimental_sandbox` find their session. The types of `ai-sdk-harness-sessions` are restated structurally (`src/definitions/workspace.ts`): it is a dev dependency only.
- In the sandbox: one bare repository per source name and sandbox (`$HOME/.ai-sdk-harness/repositories/<name>.git`, outside the sessions' working directories, where an agent climbing out of its checkout would find it), a worktree per session on `session/<id>`, and the commit it started from at `refs/ai-sdk-harness/base/<key>`. Everything derives from the session id, so a resume needs nothing stored. A source (`src/sources/`) only points `refs/ai-sdk-harness/fetched/<key>` at a commit; the checkout takes it from there.
- Everything run in the sandbox goes through `src/git/`: one `sh -c` script per step, its inputs as positional arguments, after a prelude that turns off the repository's hooks and file-system monitor (an agent may have written them). `changes()` stages on a copy of the worktree's index, never the agent's, and spells the patch's prefixes out.
- Credentials: `gitRepository()` never puts a token in the sandbox. It registers it with `addRequestTransformations` (a fresh placeholder per fetch, matched on host, path and the exact `Authorization` value, which every sandbox package swaps) and gives git the placeholder through `GIT_CONFIG_*` variables of the fetch alone; a sandbox without brokering is refused. `hostRepository()` sends Git bundles built on the host, leaving out the commits the sandbox already has.
- The folders are layered: `errors/`, `utils/` and `definitions/` are leaves, then `git/` ← `sources/` ← `workspace/` (`eslint.config.mjs`).
- Unit tests run real git against `test/host-sandbox.ts`, a stand-in sandbox on a temporary directory of the host whose `home/` is its user's home, isolated from this host's git configuration. `test/*.e2e-spec.ts` run real Claude Code sessions in a Docker Sandbox — two on one repository, a resume, a read-only mount, and a GitHub fetch with a brokered token (`GITHUB_TOKEN` or the `gh` login) — and are not part of CI. Behaviour of `sbx` 0.46 checked there: `readOnlyWorkspaces` needs a read-write `workspace` beside it.

### `ai-sdk-harness-approval`

- Isomorphic: its main entry runs in the browser too, where the components of the registry use its helpers. No `node:` import in `src/` but in `src/sandbox/` (`eslint.config.mjs`), exported apart as `ai-sdk-harness-approval/sandbox`; nothing at runtime from `@ai-sdk/harness`: its types only.
- `src/sandbox/`: a policy held by the sandbox, for Claude Code. `installClaudeCodePolicies()` copies the compiled package (`dist/`, the hook and what it imports) and the policies to `/etc/claude-code/ai-sdk-harness/` as root, and a managed-settings fragment that runs `hook/sandbox/hook-main.js` on every `PreToolUse`. Checked on Claude Code 2.1.290 through the bridge: settings and `managed-settings.d/` are read (the bridge leaves `settingSources` unset), the agent's `env` reaches the hook, a hook's `allow` does not override the bridge's `ask` rules in `allow-reads` (hence `allow-all`), and a hook's `ask` fails there without `canUseTool` (hence denied).
- A policy (`defineApprovalPolicy()`, `src/policy/`) is evaluated on the host, on what the runtime asks about, unless it is held by the sandbox (below). `agentSettings()` picks the `permissionMode` that makes the runtime ask what the policy may restrict; it decides nothing itself.
- Shell commands are read by `src/utils/shell.ts`, a scanner, not a parser: chains, substitutions and redirections it recognizes; anything it misreads must end up matching no rule, so asked about. Add a case to `shell.spec.ts` with every change.
- The folders are layered: `definitions/` is a leaf, then `utils/` ← `policy/` ← `describe/`, with `questions/` beside them (`eslint.config.mjs`).
- The components of the docs' shadcn registry (`/r/<name>.json`, `docs/lib/registry.ts`) are the files of `examples/next-chat/components/harness/`: they run there against real sessions. `test/*.e2e-spec.ts` run a policy against real Claude Code sessions and are not part of CI; the `examples/next-chat` screenshots `policy` and `questions` show the package at work.

### `ai-sdk-harness-network`

- Lists of hosts and the functions that check and merge them, nothing else: no runtime dependency, no `node:` import in `src/` (`eslint.config.mjs`), so a form in the browser checks hosts as a server does. The notation is the one `allowedHosts` of `@ai-sdk/harness` takes, which `isAllowedHost()` holds once for every package.
- The folders are layered: `errors/` and `presets/` are leaves, `hosts/` imports `errors/` only (`eslint.config.mjs`).
- A preset names each host it relies on, the domain beside its `*.` wildcard: whether `*.example.com` covers `example.com` differs from one sandbox to another. `HARNESS_NETWORK` and `PROVIDER_HOSTS` stand in for what the `@ai-sdk/harness-*` and `@ai-sdk/<provider>` packages do not publish yet: read from each adapter (the packages it installs, the hosts its credentials are brokered to) and each provider package (its default `baseURL`).
- `test/*.e2e-spec.ts` fetch from each trusted service, redirects followed, in a Docker Sandbox closed to all but `trustedHosts()`, and check the proxy refused nothing (`blockedRequests()`); they run a Claude Code and a Codex turn with `harnessHosts()` alone. A new service comes with its sample URLs there. Not part of CI: run them when a preset changes.

## Code conventions

- Public exports live exclusively in each package's `src/index.ts`.
- Every public symbol carries TSDoc comments, which the docs' `<AutoTypeTable>` reads.
- Publishable packages declare `"type": "module"`, `"sideEffects": false`, `"engines.node": ">=24.0.0"`, and treat `@ai-sdk/*` packages as **peer** dependencies (and as devDependencies for local tests).
- Relative imports carry their `.js` extension (`nodenext`).
- Unit tests live next to the source as `*.spec.ts`; e2e tests live in `test/*.e2e-spec.ts`. Both run under Vitest.
- Documentation content is written in English only.
- Never edit generated files by hand: `CHANGELOG.md` (written by Changesets), `docs/.source`, `next-env.d.ts`, and the blocks between `BEGIN:` / `END:` markers in `AGENTS.md` and `docs/AGENTS.md`, which `turbo` and `next dev` rewrite.

## Versioning

- Any user-visible change to a publishable package requires a changeset (`pnpm changeset`). Write it for the people who install the package: it lands verbatim in its `CHANGELOG.md` and its GitHub release. The example, the docs site and the `@repo/*` presets never need one.
- In the 0.x series, a breaking change is a `minor` with a `BREAKING:` note in the changeset body, anything else a `patch`. Never write a `major` changeset: it would release 1.0.0, a step the maintainers take on purpose.
- Never change a package's `version` by hand, nor run `pnpm version-packages` or `pnpm release`: releases go through CI, as `MAINTAINERS.md` describes.
- The versions a README names (`<package>@x.y.z`, `<package>:x.y.z`) follow its `package.json`, pinned by the release pull request (`scripts/sync-readme-versions.ts`) and checked by the CI: never bump them by hand.

## Commits

- Commits follow [Conventional Commits](https://www.conventionalcommits.org), checked by commitlint on every commit and in CI. The scope is the package folder (`sandbox-sbx`, `sandbox-microsandbox`, `sandbox-cloud-run`, `sandbox-runtime`) or the area (`docs`, `ci`, `deps`, `eslint`…).
- Pull requests are squash-merged with their title as the commit message, so the title follows the same convention.
- The pre-commit hook runs lint-staged and `pnpm typecheck`. Never bypass the hooks (`--no-verify`): fix what they report.

## Available commands

### Mandatory validation before delivery

Every change must pass:

1. `pnpm format:check`
2. `pnpm lint`
3. `pnpm typecheck`
4. `pnpm test`
5. `pnpm build`

Add when the change touches the matching area:

- `pnpm --filter ai-sdk-harness-plugins test:e2e` when changing how plugins reach a runtime (needs Docker Sandboxes and a credential, or the CLI login, of Claude Code and Codex).
- `pnpm --filter ai-sdk-harness-sessions test:e2e` when changing how sessions start, suspend or resume (needs Docker Sandboxes and a credential, or the CLI login, of Claude Code).
- `pnpm --filter ai-sdk-harness-workspace test:e2e` when changing what the workspace runs in the sandbox or how a source fetches (needs Docker Sandboxes and a credential, or the CLI login, of Claude Code; `GITHUB_TOKEN` or the `gh` login for the brokered fetch).
- `pnpm --filter ai-sdk-harness-network test:e2e` when changing a preset (needs Docker Sandboxes and a credential, or the CLI login, of Claude Code and Codex).
- `pnpm --filter ai-sdk-harness-approval test:e2e` when changing how a policy reads a call or answers it within a turn (same needs).
- `pnpm --filter ai-sdk-sandbox-sbx test:e2e` when changing how the package drives `sbx` (needs Docker Sandboxes on the machine; `SBX_E2E_CLOUD=1` adds the cloud mode).
- `pnpm --filter ai-sdk-sandbox-microsandbox test:e2e` when changing how the package drives the `microsandbox` SDK (needs KVM or Apple Silicon, and a runtime of the SDK's version: an `msb` installed in `~/.microsandbox` wins over the bundled one; otherwise point `MSB_HOME` at another, short, directory).
- `pnpm --filter ai-sdk-sandbox-runtime test:e2e` when changing how the package drives srt or the supervisor (needs `bwrap`, `socat`, `rg` and a Claude Code credential; `SRT_SOCAT`, `SRT_RIPGREP` and `SRT_ALLOW_ALL_UNIX_SOCKETS=1` adapt it to the host).
- `CLOUD_RUN_SANDBOX_URL=… pnpm --filter ai-sdk-sandbox-cloud-run test:e2e` when changing how the service drives the `sandbox` CLI (needs the service deployed on Cloud Run, the gcloud account an invoker).
- `pnpm docs:build` when editing anything under `docs/` or a README it includes.
- `pnpm screenshots` when changing the interface of `examples/next-chat`: the docs and the READMEs show its screenshots (needs Docker Sandboxes, a Claude and an OpenAI credential).
- `pnpm pack:dry-run`, `pnpm publint`, and `pnpm attw` when editing a publishable package's manifest or its public exports.

No change is considered ready while any required step fails.
